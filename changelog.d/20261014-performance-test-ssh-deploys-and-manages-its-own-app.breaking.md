`psynet performance-test ssh` now only runs on apps that it deployed for performance tests, never on an existing deployment, because the tests fill the app's database with bots and may reset it. If the server has no app named `--app`, it deploys the experiment from the current directory in debug mode, as `psynet debug ssh` does and with the same `--server`, `--dns-host`, `--ingress`, `--use-local-dallinger` and `--yes` options, so you no longer run `psynet debug ssh` first; like `psynet debug ssh`, that deploy resets your local debug database. The app's config sets the new `performance_test_app` variable, which the command reads inside the app's web container. At the end of the run, even one that fails or is interrupted, the command destroys the app, but only if its `docker-compose.yml` still records the ID that this run's deploy or update wrote, so it never destroys an app that someone else deployed; pass `--keep-app` to keep it, for example to inspect its dashboard and logs; with `--reset-database`, only a kept app has its database restored at the end of the run. A later run with the same `--app` updates the kept app in place, keeping its database. Apps without the mark, such as one deployed with `psynet debug ssh`, and apps whose deploy never finished launching the experiment are refused, and never destroyed, with advice on what to do instead. Setting `performance_test_app = true` in `config.txt` yourself declares that the app's data is disposable, and `psynet deploy ssh` refuses to deploy with it set. Your computer now runs the series of tests or the capacity search, one test at a time in the app's web container, with the same options, test lengths and summary as a local run, and `--json-output` works with `performance-test ssh`.
