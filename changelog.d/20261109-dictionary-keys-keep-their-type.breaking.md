Dictionaries stored in the database, such as `participant.var`, `trial.var`, `node.var` and trial answers and definitions, now keep the type of their keys. Before, integer keys silently came back as strings, so `participant.var.choice_by_player = {12: "rock"}` read back as `{"12": "rock"}`. Now it reads back as `{12: "rock"}`, and `choices[participant.id]` works. Look up keys with the type you stored them with: code that stores integer keys but reads them as strings, for example `choices[str(participant.id)]`, must use the original keys instead, while code that stores `str(participant.id)` keys must keep reading `str(participant.id)` or change the write and the read together; converting with `int(key)` while iterating works for both. A dictionary with both string and non-string keys keeps its key types but not its key order: string keys come first. JSON turns integer, float, boolean and `None` keys into strings, so pages, routes and bot responses receive `{"12": "rock"}`. Tuple keys make any conversion to JSON raise `TypeError`, as do keys that cannot be compared, such as an integer and a string or an integer and `None`, when your own code sorts keys, for example with `json.dumps(value, sort_keys=True)`; convert the keys first, for example with `{str(k): v for k, v in d.items()}`. In the database and its exports, a non-string key is written in jsonpickle's tagged form, for example `{"json://12": "rock"}`, as tuples and other non-JSON values already were; `psynet.export.unpack_json_column` removes the tag, so this becomes a column named `12`, or `json://12` if the same dictionary also has the string key `"12"`. Dictionaries stored with string keys, including any stored before this change, are unchanged, except that a string key stored before this change that starts with `json://`, such as `"json://12"`, is now read back as the key it names, here `12`.
